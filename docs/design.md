# homecloud — design

Status: **P1 done; local API, web app, desktop app and drive health live (M1–M4). No deletion capability exists yet.** · Last reviewed: 2026-10-05

Sections 4–7 mix what is built with what is planned; each planned part is marked *(planned)*.

## 1. Goal

Make a local drive (E:) the single, verified home of the owner's iCloud data — iCloud Photos (≈3,765 assets / 315 GB, 285 GB video), iCloud Drive, and iPhone backups — while iCloud itself keeps only the most recent 30 days. Fully automatic, auditable, and fail-closed: nothing is ever removed from iCloud unless it is provably safe on disk.

## 2. Principles

1. **One code path per job.** No fallback sources, no duplicate stacks, no compatibility shims. Abstractions only when a second real implementation exists.
2. **Nothing hardcoded.** Paths, ports, limits, schedules and pinned tool versions live in a strictly validated TOML config.
3. **Fail closed.** Any doubt — hash mismatch, stale data, failed health check, unconfirmed deletion — means *do nothing and alert*.
4. **Public interfaces only.** External tools are driven through their CLIs and documented outputs (e.g. `kei manifest --format json`), never their internal databases.
5. **Verified dependencies.** Latest stable releases of official or actively maintained projects, each cited in §9.

## 3. Why build this (alternatives evaluated)

| Option | Verdict | Evidence |
|---|---|---|
| icloudpd "Move" mode | Rejected as deleter | Deletes assets whose download failed (#1312, open); >1 GB videos truncated (#1311, open); seeking a maintainer since 2026-01 (#1305) |
| kei | **Adopted as downloader** | MIT, active (v0.26.0, 2026-10-23), checksum-verified downloads, JSON manifest; iCloud deletion is an explicit non-goal (product charter) |
| pyicloud (timlaing fork) | **Adopted as deletion transport** (sidecar) | MIT, 2.7.0 (2026-09-04), CloudKit `PhotoAsset.delete()`; bug #353 (per-record errors discarded) ⇒ every delete is re-confirmed |
| PhotoSync / Immich / Ente | Not the pipeline; **Immich adopted as the optional read-only viewer** (§10 Spike D) | iOS requires a user tap to delete from the phone library; background upload is OS-scheduled |
| iCloud for Windows sync folder | Not used by homecloud | Download throttled (~1 MB/s measured); cannot relocate off C:; on-demand reads time out |
| Write our own iCloud client | Rejected for Photos; **adopted for iCloud Drive** (§8f) | For Photos it would re-implement the SRP/2FA/CloudKit surface kei and pyicloud already maintain; for Drive no maintained tool archives without deleting (§8f) |

Process model: a **per-user process launched at logon** by a Task Scheduler user task (`homecloud install`). Not a Windows service: services run in Session 0, which cannot interact with the user's session.

Data layout (root is the required `storage.root`, e.g. `D:\Archive` or `/srv/homecloud`; no default): `homecloud-archive.json` (the archive's identity, §8d), `Photos\` (kei-owned; `Photos\Hidden\` for photos hidden in iCloud), `Drive\` (the iCloud Drive archive, §8g), `iPhone backups\` (copies of iPhone backups, §8e), `kei\` (the generated kei config and its sync report; kei's own state lives in `%USERPROFILE%\.config\kei`, §10), `homecloud.db`, `manifest.csv`, `safe-to-delete.csv` (§7), `README.txt` and `.cache\thumbnails\` (hidden, derived). Logs live outside the archive (§8l); ledger snapshots go to `backup.dir` on another drive (§6). *(planned: `deletions.jsonl`, P3.)*

## 5. Ledger

Core schema (migrations 0001, 0002 and 0007; the others are described with their feature) (`internal/ledger/migrations`; STRICT tables, RFC 3339 UTC text timestamps):

- `assets(library, asset_id, state, state_changed_at, created_at, added_at, last_seen_at)`
- `resources(library, asset_id, version, filename, local_path, media_type, size_bytes, kei_sha256, verified_content_at, verified_structure_at, verified_probe_at, last_scrub_at, failure, requires_structure, requires_probe)` — one row per rendition (kei manifest grain)
- `rendition_repairs(library, asset_id, version, requested_at, set_aside_at, kept_as)` — migration 0007: one row per failing rendition of a repair in progress, deleted when it completes or is abandoned
- `runs`, and append-only `events` (triggers reject UPDATE/DELETE). The API lists events by kind and, optionally, by the text of their subject, the name the app shows for them (a Photos asset's original file name, an iCloud Drive path, an iPhone's name): SQLite's own `lower()`/`LIKE` fold ASCII only, so the ledger registers `homecloud_fold` (Unicode case folding of the decomposed text, combining marks dropped: Apple stores names decomposed, Greek is typed without accents) and matches with `instr`; a scan of the event log, which needs no index at this size. *(planned, P3: `deletion_batches`)*

State machine (implemented): `discovered → downloaded → verified`; any state → `quarantined` (mismatch); `quarantine release` returns an asset with an audited reason. A file kei replaces or moves keeps its recorded failure, so a quarantine lasts until it is released or repaired.

Repair (implemented, `RepairQuarantine` / `quarantine repair`): for a file that is damaged on disk while iCloud's copy is fine. kei only downloads a file again once its state marks it failed: `kei reconcile` does that for a recorded file that is **missing** or truncated (kei v0.26.0 `src/commands/reconcile.rs`; a same-size corrupt file is not detected, and replacing a truncated file in place needs the one-shot `kei sync --repair-truncated`), and a normal sync then retries failed files at their recorded path. So the repair takes the file away rather than asking kei to judge it:

1. The request records a row per failing rendition (`quarantine_repair_requested`); the failures stay until the repair completes, and a release is refused meanwhile (`ErrRepairInProgress`).
2. The next cycle, before downloading, moves each file through an `os.Root` on `storage.root` to `Damaged/<request time, UTC>/<path inside Photos>`, outside kei's download folder, and records it (`rendition_set_aside`, with `kept_as`; empty when the file was already missing). The destination is derived from the request, so a file moved by an attempt that stopped before recording it is found there. Files in `Damaged/` are never deleted by homecloud.
3. It runs `kei reconcile` and reads kei's manifest. A rendition kei will not download again is a refusal: kei no longer lists it, its settings exclude it, or its record still says downloaded from before the file left (reconcile leaves kei's protected legacy records unchanged). The asset's files are then put back, the empty folders removed, the repair abandoned (`quarantine_repair_abandoned`, with the reason) and an alert sent; the asset stays quarantined.
4. kei sync downloads the failed files. Ingest completes the repair once every rendition of it is downloaded again with kei's `downloaded_at` at or after the set-aside time (kei records whole seconds, so that time is truncated to the second): the renditions lose their failures and all verification evidence, the asset returns to `downloaded` (`quarantine_repaired`), and the same cycle runs every tier on the new files. A file that fails again is quarantined again. *(planned, P3: `→ eligible → delete_requested → delete_confirmed → purged_expected (+30 d)`; quarantine on an unconfirmed delete; remote change → `changed_remote → discovered`.)*

## 6. Verification tiers

1. **Content:** SHA-256 of the file on E: equals kei's recorded download SHA-256; size equals the manifest size. A missing file is a mismatch (the expected bytes are not there); every cycle first confirms the configured archive is present, so a missing drive is never mistaken for missing files.
2. **Structure (`.mov`/`.mp4`/`.m4v` video only, per `verify.RequiredTiers`):** MP4/QuickTime top-level box walk — contiguous chain ending exactly at EOF, containing `moov` and `mdat`; `ftyp` first only for ISO-BMFF extensions (see §10) — catches truncation.
3. **Probe (video):** `ffprobe` reports streams and a positive duration consistent across container and streams. Only ffprobe exiting non-zero counts against the file; failing to start ffprobe is retried, never quarantined. Each run is bounded (5 min).

Scrub (implemented): after a cycle, when `schedule.scrub_interval` has passed since the last *completed* scrub, the agent re-hashes `schedule.scrub_fraction` of verified renditions (rounded up, at least one), those whose content was confirmed longest ago first (`resources.last_scrub_at`: set by every content pass, cleared when the file changes or fails; exported as `verified_at` in `manifest.csv`). With 5 % weekly the whole archive is re-read every 20 weeks. A changed **or missing** file is a mismatch: the content tier's pass is cleared, the asset is quarantined (so P3 never deletes it from iCloud) and an urgent alert is sent. Missing files only count when the configured archive volume is mounted; otherwise the run fails without touching anything and is retried at the next cycle. Unreadable files are retried first next run. Each scrub is a `scrub` run with a `ScrubReport`; a run that could not do its work records an `error` in its report, and only runs without one count for the schedule.

Ledger backup (implemented): every `backup.interval` the agent writes `homecloud-<UTC time>.db` to `backup.dir` with `VACUUM INTO` (one consistent view of the live ledger), runs `PRAGMA integrity_check` on the copy, and only then renames it into place; the newest `backup.keep` snapshots are kept and nothing else in the directory is touched. Partial snapshots left by an interrupted backup are pruned too. Doctor requires `backup.dir` to be on a different volume than `storage.root`. A failure is retried every cycle and alerts at most every `notify.repeat_every`. Each backup is a `ledger_backup` run. Restoring: stop the agent, delete `homecloud.db-wal` and `homecloud.db-shm` (a stale write-ahead log would be replayed onto the restored file), then copy a snapshot over `<root>/homecloud.db`.

## 7. Deletion

**Safe-to-delete report (implemented, read only — the rollout's report stage).** homecloud lists the iCloud Photos items the owner may delete in Apple's Photos app and deletes nothing itself. `policy.Judge` (pure, no I/O) decides per asset from `ledger.EachArchivedAsset` (every asset with a file on disk, its renditions' evidence, whether a repair is under way), and gives `eligible` or the first unmet condition, in this order:

1. *not verified*: the asset is `verified`, its original of the asset's own medium is on disk, every rendition passed each tier it requires and none has a recorded failure, and no repair is under way (`rendition_repairs`);
2. *awaiting scrub*: every rendition's checksum was confirmed after its last tier pass, i.e. by a scrub that read it back from disk (a pass records `last_scrub_at` at its own time, a scrub later). Compared in Go: the ledger's RFC 3339 text has a varying number of fractional digits, so SQL string comparison would order `…15Z` after `…15.5Z`;
3. *too recent*: `added_at` (added to iCloud Photos) is at least `safe_to_delete.min_age` (24h–87600h) ago; an unknown `added_at` fails.

The whole report is withheld (nothing listed, the reason given) unless the agent's latest storage check (§8b, made every cycle) is `ok`; before the first check after a start it is withheld too. Sizes are the sum of an asset's archived files (original, edits, Live Photo video, RAW), about what deleting it frees in iCloud. Not checked, because kei's public output does not report it yet: whether the item is still in iCloud. kei records a deletion in iCloud (`is_deleted`, `deleted_at` on its asset row, since v0.10.0, rhoopr/kei#230) and keeps the local file, but `kei manifest` has no such column and lists the asset with its old status, and `kei status` prints only a count ("Source deleted"; kei v0.26.0 `src/state/db/reports.rs`, `src/commands/status.rs`). Reading kei's database would break principle 4 (its schema changes between releases), so an item the owner already deleted stays listed until kei's manifest carries it (rhoopr/kei#708, kei's v0.27 milestone; homecloud #16). Outputs: `safe-to-delete.csv` at the archive root after every cycle (newest first; header only while withheld), and the API's `GetSafeToDelete` (totals, the counts per unmet condition, and per-month totals in the viewer's IANA time zone, so they match the months the app groups items under; the agent embeds `time/tzdata`, as Windows has no zone database) and `ListSafeToDelete` (pages newest first, keyset on capture time and asset id as `ListAssets`, judged again per page). The app's Safe to delete page shows both. Live baseline (2026-10-10): 3,899 verified assets, but only ~300 of 6,041 files re-hashed by a scrub since their verification (5 % weekly), so the list fills over ~20 weeks.

**Automatic deletion** *(planned, P3; nothing below is implemented)*. Eligibility is a pure function; **all** must hold:

- every resource of the asset (original, Live Photo video, RAW, edits) verified at its required tiers;
- `added_at_utc` older than `retention_days`;
- remote version equals archived version, and the asset was seen remotely within 24 h;
- not quarantined; match established by content hash + asset ID (never by name alone);
- health OK (the configured archive present, disk healthy, free space ≥ threshold), ledger `integrity_check` OK, scrub clean within 7 days;
- clean-history streak ≥ configured days; enable-file present; kill-file absent;
- batch within caps (initial 50 assets / 20 GB per run, ramping monthly).

Execution: write the batch to `deletions.jsonl` (fsync) → sidecar re-fetches each asset and compares filename/size/version → deletes → re-fetches to confirm `isDeleted` → unconfirmed ⇒ quarantine + alert. Apple's *Recently Deleted* (30 days) is the final undo.

Rollout (each stage enabled explicitly by the owner): report-only (2 weeks) → dry-run (3 weeks) → canary (test album, restore drill) → capped automatic.

## 8. Phases

- **P0** — toolchain, repo, CI, this document; spikes: (A) kei `asset_id` ↔ pyicloud identity on 20 assets (gate for P3), (B) kei auth/manifest representation of Live Photos/edits/`added_at`/exit codes, (C) console-less logon launch; `homecloud doctor`.
- **P1** — kei full sync, ledger, verification, status UI, ntfy. One-time in-session reconciliation of the interim archive, then its removal.
- **P2** — local encrypted iPhone backup + monitor (milestone A, implemented — §8e); homecloud's own iCloud sign-in (milestone B1, implemented — §8f); iCloud Drive archive (milestone B2, implemented — §8g) and its app views (B3, implemented: Overview card and sign-in banner, Activity "iCloud Drive" tab and events, Settings group; the API's Overview carries Drive totals and the session's sign-in time, never the session itself).
- **P3** — staged deleter; its report stage, the safe-to-delete report (§7), is implemented.

## 8a. Platforms, API and GUI (decided 2026-10-05)

- **Platforms:** Windows and Linux are both first-class for the agent and CLI. OS-specific behaviour lives only in `internal/platform` (`*_windows.go` / `*_linux.go`); business logic never branches on `runtime.GOOS`. Unsupported operating systems fail to compile rather than run degraded.

  | Concern | Windows | Linux |
  |---|---|---|
  | Two paths on one volume (doctor: `backup.dir` off the archive's drive) | volume GUID names of both (`GetVolumeNameForVolumeMountPoint`) | device numbers (`st_dev`), which bind mounts in containers keep |
  | Drives under a path (drive health) | the volume (GUID name `\\?\Volume{…}\`) → `IOCTL_VOLUME_GET_VOLUME_DISK_EXTENTS`: every disk of a spanned, striped or mirrored volume | `statx(STATX_MNT_ID)` → the mount's `major:minor` in `/proc/self/mountinfo` → `/sys/dev/block/<maj:min>` (btrfs reports an anonymous number: its source names a device, `/sys/fs/btrfs/<fsid>/devices` lists all); then down `slaves/` through device-mapper (LVM, dm-crypt) and md to the drives, a partition's drive being its parent; md arrays' state from `/sys/block/<md>/md`; each drive's node found under `/dev` by device number (so `/dev/disk/by-id/…` passed into a container works). No root needed |
  | Free space | `GetDiskFreeSpaceEx` | `statfs` `Bavail × Frsize` |
  | Single instance | `Local\` named mutex | `flock(LOCK_EX\|LOCK_NB)` on `$XDG_RUNTIME_DIR/homecloud/agent.lock` |
  | Start at logon | Task Scheduler logon task (`schtasks /XML`) | systemd `--user` unit, `Type=notify`, `Restart=on-failure` (linger for headless hosts) |
  | Agent logs | size-rotated files in `%LOCALAPPDATA%\homecloud\logs` (`internal/logfile`), crash reports beside them (§8l) | stderr → journald with syslog priorities (or the container runtime) |
  | Windowless build | `-ldflags=-H=windowsgui` | n/a |

  kei's Linux binaries require glibc ≥ 2.39 (Ubuntu 24.04 / Debian 13+).
- **Process model:** the agent is always a separate, headless process that owns the ledger, kei, verification, notifications and (later) deletion. No GUI ever hosts it.
- **Local API (implemented, M1):** Connect-RPC (connect-go v2: only a `*connect.Error` the agent writes reaches a caller with its message, any other error arrives as a bare `unknown`; requests are capped at `maxRequestBytes` and carry no compression; every route `connecthttp.Mount` registers, the per-service catch-all included, sits behind the credential and size checks), contract `proto/homecloud/agent/v3/agent.proto`, Buf v2 config with local plugins pinned as Go `tool` dependencies; generated Go code committed under `gen/`; CI runs `buf lint`, a generated-code drift check and `buf breaking` (PR base, or the previous commit on push).
  - Transport: plain HTTP/1.1 on the loopback `web.listen` (Connect unary + server streaming work over HTTP/1.1; browsers never use h2c). No server-wide write timeout because `WatchOverview` streams; read timeouts stay.
  - Request pipeline: exact Host check (`web.listen`) → Origin allow-list (own origins + the Tauri webview origins `http://tauri.localhost` on Windows and `tauri://localhost` on Linux) → CORS (`internal/web/cors.go`, the Fetch standard's CORS protocol for a fixed policy: the desktop origins only, connect-cors' method and header lists plus `Authorization`, no credentials; an allowed preflight gets 204, a refused one 403 without any CORS header; no `Access-Control-Allow-Private-Network`: Chrome paused Private Network Access, its successor Local Network Access uses a permission and exempts loopback, and WebView2 sends no such preflight header to the agent, observed 2026-10-06) → security headers → authentication.
  - Credentials (paired devices: §8j): a 256-bit bearer token generated at every agent start and published in `agent.json` (per-user state dir) — created on Windows with a protected owner-only DACL `D:P(A;;FA;;;<user SID>)` via `CreateFile` (Go's file mode bits do not set ACLs on Windows), mode 0600 on Linux, written atomically. Browsers get an in-memory session cookie (`HttpOnly`, `SameSite=Strict`, `web.session_ttl`) by exchanging a single-use 8-character sign-in code (2 min, issued only to bearer holders); cookie calls also pass `http.CrossOriginProtection`. No `Secure` attribute: plain HTTP on loopback. **Hardened 2026-10-07:** codes have a purpose (sign-in or pairing; one is refused for the other, so a sign-in link shown on a screen cannot mint a device token that never expires); wrong codes are limited to 5 a minute for all callers together, without discarding codes (a global "5 wrong guesses clear every code" let anyone who could reach the agent keep the owner from signing in); the connect page fills in a code from its link but sends it only when the owner presses Connect. On this computer the browser app lives at `http://homecloud.localhost:<port>` (`web.BrowserHost`): browsers resolve every `*.localhost` to the loopback address themselves (verified with Chrome and Edge on this PC; Firefox since bug 1220810) and keep cookies by host name, not port, so the session cookie never reaches another service on 127.0.0.1 (NotepadLLM, dev servers). A session is issued only there or at the public origin; a browser opening `127.0.0.1:<port>/` is redirected there (the fragment, with the route and any code, survives the redirect). Sessions end with `SignOut` (this browser) or `SignOutBrowsers` (all), and Settings counts them. A request authenticates as an `auth.Principal` (the agent, a device id, or a session's handle, never its cookie), which `auth.Valid` re-checks for whatever outlives the request: an overview stream ends within 30 s of a revocation or sign-out, and media links, which carry their principal under their HMAC, stop at once. Requests may not be compressed (a small gzip body inflated before anyone signed in) and are capped at 1 MiB. Sign-ins, wrong codes, pairings, revocations and sign-outs are logged; requests refused for their Host or Origin are logged once a minute with a count.
  - Versioning: an incompatible API change gets a new proto package (`homecloud.agent.vN`), so an outdated client fails with `Unimplemented`. CI runs `buf breaking` per version against the previous commit: a version must stay compatible with itself, and a new version is the deliberate break. Current: **v3** (2026-10-07: `Overview.storage_health` reports every drive under the archive and its md arrays, replacing the single drive's health; v2 on 2026-10-06 replaced the volume's identity with the archive's id); `GetInfo`'s `api_version` is informational. The agent and the desktop app ship from the same commit. Destructive actions (P3) will require a per-request confirmation nonce recorded in the ledger.
  - `web.listen` must be `127.0.0.1:<port>`: it is the address the desktop app's CSP allows. A missing archive drive is answered with `FailedPrecondition`, which the app shows as such instead of "agent unreachable"; only transient errors (`Unavailable`, `DeadlineExceeded`, `Aborted`, `ResourceExhausted`) are retried by the app.
  - Rejected: Tauri `plugin-http` (Rust-side fetch; server-streaming support undocumented), cookie-only auth inside Tauri (third-party cookie context), h2c (no browser support, not needed).
- **GUI (implemented, M2–M3):** one React 19 + Fluent UI v9 single-page app (`ui/`), hosted (a) by the agent itself (embedded with `go:embed`) for browsers and Linux/headless hosts, and (b) in a Tauri 2.12 desktop shell (`desktop/`). The design reference is the canvas linked from the plan; Fluent's `webLightTheme`/`webDarkTheme` follow the OS setting unless the user picks light or dark (Fluent ships no separate Windows 11 theme).
  - Routing is hash-based so both hosts work without server rewrites: `ui/src/app/router.ts` (about 80 lines; `useSyncExternalStore` over `hashchange`, a typed union of paths, real `<a href="#/…">` links, push or replace). An address that names no page shows the overview and is corrected in place. Every page starts at its top, also after back or forward (dashboards and lists reload their data, so a restored offset would point at different content). It listens to `hashchange` (Baseline widely available since 2015), not the Navigation API: that is Baseline only since 2026 and enabled by default in WebKitGTK only from 2.52 (2.48 and 2.50, still on some Linux systems, ship it off). Pages are not kept alive with React's `<Activity>`: they are views of the agent's data that reload on entry, and hidden copies would hold large DOM (the library grid) and stale state. Data: Connect-Query for unary calls; one app-wide `WatchOverview` stream with exponential backoff, which also refetches all queries after a reconnect.
  - Browser auth: `homecloud open` → sign-in code in the link to `http://homecloud.localhost:<port>` → Connect → `ExchangeLoginCode` → session cookie. Desktop auth: the Rust side reads `agent.json` (`agent_endpoint` command) and the web app sends the bearer token directly (native fetch + exact-origin CORS); on `Unauthenticated` (agent restarted with a new token) it re-reads the file and retries.
  - The shell grants the webview only `core:default` and seven app commands: `connection_settings` and `connection_credentials` (this PC's agent from its discovery file, or a paired homecloud and its device token from the credential store), `connect_remote`, `use_this_pc` and `device_name` (pairing, §8j), `start_agent` (runs the logon task / systemd unit), `reveal_in_folder` (reveal only; nothing is opened or executed). Plugins: single-instance, window-state, opener (used from Rust only), log. NSIS installer in `currentUser` mode; WebView2 via the download bootstrapper.
  - CSP is set in `tauri.conf.json` (`connect-src` limited to IPC and `http://127.0.0.1:*`). Verified on the built app: Griffel's runtime `<style>` injection works with Tauri's CSP handling, so no CSP relaxation beyond `style-src 'unsafe-inline'` is needed.

## 8b. Archive drive health (implemented, M4; every drive and md array since NAS milestone 5)

The archive is the only copy (no second copy, by decision), so after every cycle the agent finds the drives holding it (`platform.StorageOf`, §8a: every disk of a Windows volume; on Linux the drives under LVM and md RAID, as on a UGOS Pro pool: md raid1 → LVM → ext4 or btrfs), reads each drive's own SMART data and the state of each md array, and judges them in `internal/health`.

- **Windows:** `IOCTL_STORAGE_QUERY_PROPERTY` with `StorageDeviceProtocolSpecificProperty` reads the NVMe SMART / Health log (log page 02h) through a handle opened with no access rights, so it works from the non-elevated agent (verified on this PC at Medium integrity). The bus type comes from `STORAGE_DEVICE_DESCRIPTOR`; the model and serial number from the drive's Identify Controller data (`StorageAdapterProtocolSpecificProperty`, `NVMeDataTypeIdentify`, CNS 01h; bytes 4–23 and 24–63), because for NVMe drives the descriptor's serial number field holds the namespace's EUI-64 (`0025_385C_1190_32F6.` on this PC's Samsung 970 EVO Plus). Non-NVMe drives report "unavailable": reading ATA SMART on Windows needs administrator rights. Rejected: WMI `MSFT_PhysicalDisk.HealthStatus` through `microsoft/wmi` (the library panics on COM initialisation failure and sets process-wide COM security; the native query also gives richer data), and `Get-StorageReliabilityCounter` (needs elevation).
- **Linux, `drive_health.source = "udisks"` (desktops):** udisks2 over D-Bus (`godbus/dbus/v5`): `Manager.ResolveDevice` with the drive's device node (`path`, udisks ≥ 2.7.3, matched against `Block.Device` and its `/dev` symlinks) finds its `Drive`; NVMe drives use `NVMe.Controller` (udisks ≥ 2.10) properties plus `SmartGetAttributes`, ATA drives `Drive.Ata`. Reading needs no polkit authorization; udisks refreshes SMART every 10 minutes. Interfaces are detected by introspection.
- **Linux, `drive_health.source = "smartctl"` (servers, the container):** `smartctl --json=c --info --health --attributes <node>` (`internal/smartctl`), smartmontools 7.5 (`7.5-2~bpo13+1` from Debian's trixie-backports; trixie itself has 7.4), version pinned in `[smartctl]` and checked by doctor. Keys as smartmontools 7.5 writes them (`smartctl.cpp`, `ataprint.cpp`, `nvmeprint.cpp`, read at the `RELEASE_7_5` tag): `smart_status.passed`; NVMe `nvme_smart_health_information_log.critical_warning` and `media_errors`; ATA bad sectors = raw Reallocated (5) + Current Pending (197) sectors, as udisks counts them; 7.5's device-independent `endurance_used` and `spare_available`; `temperature.current`, `power_on_time.hours`. The exit status is a bit mask (smartctl(8)): bits 0–1 mean it could not run or open the drive (except that it also sets bit 1 for drives it identified without ATA IDENTIFY data, such as SCSI disks, so a reported protocol is checked first), bit 4 (a pre-failure attribute at its threshold) counts as a failure prediction even if the drive's own status passed. SCSI/SAS drives are reported as unavailable. Fixtures: real output captured from 7.5 in Docker (a virtual SCSI disk, permission denied, no such device) and ATA/NVMe reports built from the 7.5 source (`testdata/constructed/generate.mjs`); **to be checked against the NAS's real drives at the migration.**
- **Container permissions (verified in Docker 2026-10-07):** Docker gives a non-root container user no capabilities (moby #8460, #36587; still so in 2025, #50083). So the image gives `/usr/sbin/smartctl` file capabilities `cap_dac_override,cap_sys_rawio,cap_sys_admin+ep` (`CAP_SYS_RAWIO` for ATA pass-through via `SG_IO`, `CAP_SYS_ADMIN` for NVMe admin commands, `CAP_DAC_OVERRIDE` to open the drive nodes Docker creates as `root:root 0600`). Without them in the bounding set the kernel refuses to start smartctl (EPERM: a file whose permitted capabilities exceed the bounding set), which homecloud reports with the compose fix. Rejected: adding the user to the disk group (raw reads of every passed drive) and a privileged container.
- **smartctl sidecar (decided 2026-10-07):** the agent parses media downloaded from iCloud, so it should hold neither the drives nor the capabilities that query them. In the container, smartctl runs in a second container from the same image (`homecloud smartctl serve`, `internal/smartctl/socket.go`): no network (`network_mode: none`), `cap_drop: ALL` plus `SYS_RAWIO`, `SYS_ADMIN` and `DAC_OVERRIDE`, a read-only system, the configuration read-only and each drive read-only by its `/dev/disk/by-id/` name (Docker resolves the symlink and creates the node at that path). It answers on a Unix socket (`smartctl.socket`) in a tmpfs volume owned by `PUID:PGID` (mode 0700) that both containers mount, never on TCP: in userspace networking Tailscale forwards tailnet connections to any loopback port (§8i). One request per connection, bounded in size and time: the drive's kernel name (refused unless it matches `^[a-z][a-z0-9]{0,31}$`), which the sidecar maps to the node it was given by device number (`platform.DriveNode`, sysfs `/sys/block/<name>/dev`); a drive not passed in has none and is reported as unsupported. Errors keep their kind across the socket, so the agent judges them as if smartctl ran there; one smartctl runs at a time. The agent container then runs with `cap_drop: ALL`, `no-new-privileges`, a read-only system and `/tmp` on tmpfs, and no devices. **Verified (2026-10-07, Docker Desktop, image `g-test`):** the sidecar ran smartctl with only its three capabilities as uid 1000; the locked-down agent's doctor read the pinned version and a drive through it; the agent container's capability sets were empty and smartctl could not start there (exit 126); with a stand-in smartctl the agent started and ran every job with its system read-only.
- **md arrays** (kernel `md.html`): `array_state` not running (`clear`, `inactive`) or `broken`, `degraded` > 0, or a member `faulty`/`blocked` = failing (one more failure loses data); `sync_action` `resync`/`recover`/`reshape` (with `sync_completed` progress), a member with `write_error`, `want_replacement` or corrected read `errors` = warning. `mismatch_cnt` is shown but not judged: on raid1 it can be non-zero without damage (md(4)), and the scrub re-checks every file. Discovery and md state are tested against the real kernel (`TestStorageOfRealStack`, opt-in with `HOMECLOUD_TEST_BLOCK_DEVICES=1` as root: md raid1 → LVM → ext4 on loop-device partitions, a failed member, and a two-device btrfs raid1).
- **Verdict** (only thresholds the standards define): per drive, any critical warning (NVMe critical-warning bits, ATA failure prediction) = failing; media/data-integrity errors or "percentage used" ≥ 100 = warning; unreadable = unavailable, never treated as healthy. The overall state is the worst of every drive and array, a reported problem outranking an unreadable drive (so a warning still alerts while another drive cannot be read); each reason names its drive or array. A change of the overall state is appended once to the event log (`drive_health_changed`) and warning/failing sends an urgent ntfy alert. `homecloud doctor` runs the same check. P3's deletion gates will require state OK.

## 8c. Library browser (implemented, M4)

- **Thumbnails** (`internal/thumbs`): the pinned FFmpeg build (`[ffmpeg]` in the config pins `ffprobe` and `ffmpeg` together) renders WebP: a 320 px square for the grid, a fit within 1600 px for the detail view (never enlarged). Verified on the archive (ffmpeg 9.0.2): tiled iPhone HEIC must be stitched from stream group 0 (`-filter_complex [0:g:0]…`, detected with `ffprobe -show_entries stream_group=index`), everything else uses the first frame; ffmpeg applies HEIF/container rotation and JPEG EXIF orientation itself (a −90° JPEG rendered portrait). DNGs (Apple ProRAW included) are rendered from their embedded preview, fed to ffmpeg on stdin (`-f jpeg_pipe` or `-f jpegxl_pipe`): ffmpeg cannot develop raw sensor data, and its TIFF decoder renders the JPEG-compressed preview IFD of an Apple ProRAW DNG (DNG 1.6: IFD0 = 4032×3024 baseline JPEG, raw in a SubIFD) as a blank frame. homecloud's own reader (`internal/thumbs/dng.go`, following TIFF 6.0, TIFF Technical Note 1 and the DNG 1.7.1.0 specification) treats a classic TIFF whose IFD0 has `DNGVersion` as a DNG, walks IFD0 and its SubIFD tree (bounds-checked reads, capped entries and IFDs, loops skipped; an entry's values are read only for the tags the walker uses, the SubIFD list only up to the IFD cap, so a file whose tags each claim most of its bytes costs nothing; on the archive's 812 DNGs it finds exactly the previews it found before), and takes the largest picture among the primary previews (NewSubFileType 1) stored as one JPEG or JPEG XL strip or tile. A JPEG candidate must pass `image/jpeg.DecodeConfig`, so the raw's lossless JPEG is never picked; a JPEG XL candidate (DNG 1.7, Compression 52546) must start with a JPEG XL signature, bare codestream or ISOBMFF container (DNG 1.7.1.0 allows both and recommends the container for previews), and its size comes from the IFD's ImageWidth/ImageLength. A JPEG XL preview goes to ffmpeg as `-f jpegxl_pipe`, which needs an FFmpeg built with libjxl (the container image's is; on Windows the Gyan full build decodes both forms, checked 2026-10-08). On the archive (10,232 photo files, 812 DNGs) it routes every file and extracts every preview exactly as the third-party library it replaced; all 812 previews are JPEG. Other camera raws (NEF, CR2, ARW…) and BigTIFF files go to ffmpeg like ordinary TIFFs; the archive has none. The preview's own EXIF orientation is applied by ffmpeg. Every other format goes to ffmpeg directly, as `-protocol_whitelist file -i file:<path>` (the preview pipe: `pipe` only), so neither a path nor a crafted file (a playlist) can make a full ffmpeg build open a URL; ffprobe is called the same way. 50–160 ms per image. Files are named by the source's SHA-256, so kei moving a file keeps its thumbnail. The cache lives in `<root>/.cache/thumbnails` (hidden), is derived data, and is never consulted for verification. Each size's directory is named after a fingerprint of the ffmpeg arguments that shape it (`thumb-<8 hex>`), so changing a filter, codec or quality re-renders instead of serving stale images; at startup the agent deletes every other entry of the cache directory (`Renderer.Prune`). Each cycle ends with a "preparing previews" phase rendering missing grid thumbnails (`ffmpeg.renderers` ffmpeg processes at most); failures are logged, never fatal.
- **Media URLs** (`internal/media`): `GET /media/{size}/{library}/{asset}/{version}?exp=…&sig=…` with an HMAC-SHA256 over path and expiry, keyed per agent start. Image elements cannot send the bearer token, and cookie-free desktop requests need no session; only ledger entries can be addressed, never arbitrary paths. Expiry is rounded to 6-hour windows (valid ≥ 12 h) so repeated listings return identical URLs and browsers cache the images.
- **API/UI**: `ListAssets` pages assets newest first (keyset on capture time and asset id), filtered by kind and by Hidden (assets under `Photos/Hidden`), showing the edited version when there is one and the picture of a Live Photo. Two more filters select by capture time: `on_this_day` (a calendar date and the viewer's IANA time zone) lists the assets taken on that month and day in each year from the archive's first capture up to the year before the date's, each day being local midnight to midnight in that zone (23 or 25 hours across a daylight-saving change; 29 February only in leap years); `taken_before` lists those taken before an instant, which the app uses to start at a month. `ListCaptureMonths` counts a view's assets by the month they were taken in the viewer's zone, newest first, for the month picker. Capture times are compared as instants (`unixepoch(created_at, 'subsec')`, SQLite 3.54.1 in modernc.org/sqlite v1.61.0, to the millisecond), not as text: the stored RFC 3339 has a varying number of fractional digits, so `…00.5Z` would sort before `…00Z` and fall outside a day it belongs to. The web app groups by month, loads more on scroll, and shows the preview, renditions and path. Its "On this day" view (`#/library?view=on-this-day`) lists today's photos from earlier years by year, and the Overview shows six of them with a link there, nothing on a day without any; the month picker lists the months that have photos, with their counts, and starts the timeline at the chosen one (`?month=2023-06`, sent as `taken_before` the first instant of the next month in the viewer's zone); the desktop app adds "Show in folder" and allows `http://127.0.0.1:*` images in its CSP.

## 8d. Agent cycle and maintenance (implemented)

- **Preflight, every cycle:** the configured archive must be present at `storage.root`: `homecloud-archive.json` there (written once by `homecloud archive init`, `internal/archive`) must name `storage.archive_id`. An unmounted drive, another disk or an empty mount point has no marker or another one. The marker travels with the files, so an archive copied to another disk or a NAS keeps its identity, and it needs nothing from the OS, so it works the same in containers and on network shares (a volume's own identity does not). Without it the cycle stops before kei, ingest or verification runs, records a failed run (`archive_unavailable`) and alerts. Below `storage.min_free_percent` the download is skipped (`skipped_low_space`) while ingest and verification still run. Lasting conditions (sign-in needed, drive missing, low space, a backup problem) alert at most every `notify.repeat_every`; the last alert per condition is kept in the ledger (`alert_throttle`), so restarting the agent does not repeat it early.
- **iCloud Photos activity (#22):** after a cycle whose kei sync listed every change since its checkpoint (exit OK or partial, a report with no enumeration error, no incomplete or interrupted listing, no inventory drop: `kei.Report.ListedCompletely`), the agent compares the ledger's newest `added_at` with `icloud.quiet_after` (24h–8760h). Older means the phone may have stopped uploading (iCloud Photos off, iCloud storage full) and photos taken since may exist only on it: found on 2026-10-24, when nothing had been added since 2026-04-17 while every sync ended OK. The state (`active`/`quiet`) is appended once per change (`photos_activity_changed`, with the newest addition and the threshold), the alert repeats every `notify.repeat_every` while it lasts and names no file or device, and the Overview shows the newest addition and, while quiet, a warning banner. A failed or partial listing judges nothing, so a broken sync never looks like a quiet library; an empty library has nothing to fall quiet. `homecloud doctor` does not report it: doctor reads no ledger.
- **Viewer (optional, #21):** with `[viewer]` set, the cycle ends after previews. When files changed, it queues Immich's scan of `Photos/`, then stacks each edit over its original (§10, Spike D). The viewer is derived data: a failure is logged, never fatal.
- **Maintenance:** after each cycle the agent runs each maintenance job (scrub, ledger backup, iPhone backup check, iCloud Drive sync) when no *completed* run of that kind falls within its interval (`runs.detail` carries `error` only when a run could not do its work). A job therefore runs at the first cycle at or after it is due; the overview reports each job's next run computed by the same rule (`app.NextRunAt`), so the app never re-derives it.
- **Interrupted runs:** on Windows the agent is a GUI-subsystem process that receives no console events, so logoff or shutdown ends it without notice. Every write is crash-safe (SQLite WAL, atomic renames, kei's own journal), and at startup the agent closes every run left unfinished as failed with `interrupted`. Only one agent runs at a time, so an open run at startup was interrupted.
- **One ledger writer:** the agent holds the `homecloud-ledger-writer` lock for its whole life; `homecloud verify`, `homecloud quarantine release` and `homecloud quarantine repair` take the same lock and refuse while the agent runs (the app offers these actions).
- **Live status:** verification and scrub wake the status hub after every file; each overview stream sends at most one update per second, so live counts never turn into ledger load. A sync requested during maintenance runs right after it.
- **Child processes:** `platform.Command` starts every program (kei, ffprobe, ffmpeg, system tools) with its output captured and, on Windows, `CREATE_NO_WINDOW`. Per-file tools are bounded (`ffmpeg.probe_timeout`, `ffmpeg.render_timeout`), `kei manifest` by 10 minutes (it reads kei's local state: 6,041 renditions take about a second); a shared thumbnail render is detached from the request that started it. Every command has `WaitDelay` (10 s): once a program exits or is cancelled, Wait no longer waits on pipes a program it started still holds. Captured output is bounded (`tool.Tail` keeps the last kilobyte of diagnostics, `tool.Head` the first megabyte of ffprobe's report, more than any recording's streams fill). Files are checked `verify.workers` at a time.

## 8e. iPhone backup monitor and copies (implemented, P2 milestone A; copies NAS milestone 6)

- **Who makes the backups:** Apple's Devices app (Windows; desktop iTunes and libimobiledevice's `idevicebackup2` write the same layout) with "Encrypt local backup" on. The password stays with the owner; homecloud never asks for it, never decrypts `Manifest.db`, and never writes into a backup folder. Backups stay where Apple's tool puts them (owner decision 2026-10-06) and homecloud never writes into them; since 2026-10-07 (owner decision) it also keeps verified copies of them in the archive (below).
- **What is read (`internal/iphonebackup`):** per device folder `<UDID>`: `Info.plist` (XML: `Device Name`, `Product Version`, `Unique Identifier`), `Manifest.plist` (binary: `IsEncrypted`), `Status.plist` (binary: `SnapshotState`, `Date`). An absent key reads as empty (a missing `IsEncrypted` makes the backup invalid); a key of another type is a plist error. Key names and types: libimobiledevice `tools/idevicebackup2.c` and The Apple Wiki "ITunes Backup".
- **Plist reader (`plist.go`, no library):** only the top-level dictionary of an XML or binary (`bplist00`) plist, chosen by its first bytes; strings (ASCII and UTF-16), booleans and dates are decoded, every other value is kept only by its type, so nested data is never followed. The binary checks follow Apple's CoreFoundation `CFBinaryPList.c` (CF-1153.18): the trailer and offset table as `__CFBinaryPlistGetTopLevelInfo` checks them, every reference and extent inside the object area, keys that are strings, a repeated key refused. XML goes through `encoding/xml` in strict mode, which applies no DTD and rejects every entity but the five predefined ones. Files over 256 MiB are refused (`Info.plist` carries every app's icon and metadata), as is a top-level dictionary of more than 4,096 entries (a backup's plists hold a few dozen) before any map is made for it, and a skipped XML value nested more than 64 levels deep (a counted skip replaces `Decoder.Skip`, whose stack of open elements would grow with the nesting); allocation-budget tests hold both to a megabyte. Test fixtures come from Python's `plistlib` (`testdata/plist/generate.py`), malformed inputs include howett.net/plist issue #90, and `FuzzBinary`/`FuzzXML` fuzz both paths. **Not yet checked against a real backup:** none exists yet (on the owner's PC the iPhone's USB link kept dropping, homecloud#15); the first real one must decode before this counts as verified.
- **Folders:** a `Snapshot` subfolder means a backup is being written; the first backup of a device may lack `Manifest.plist`/`Status.plist` until then. Folders `<UDID>-yyyymmdd-hhmmss` are archived copies: counted, not judged.
- **Verdict per device, most severe first:** invalid (plists missing/malformed, folder ≠ UDID, a completion date more than an hour in the future) › unreadable (a file could not be read in full) › unencrypted › incomplete (`SnapshotState` ≠ `finished`, no completion date, or a backup in progress that wrote nothing for `stalled_after`) › stale (finished longer ago than `max_age`) › shrunk (more than `max_shrink_percent` smaller than the last normal size, until a later backup of about the new size confirms it as normal) › in progress (nothing else is judged, and plist errors are ignored, while Apple's tool writes) › ok.
- **Reading:** every check reads the plists and stats every file; every file is read in full once per `read_interval` (it costs the whole backup's size in disk reads), and the count of unreadable files is kept until the next full read.
- **Record and alerts:** a maintenance job (run kind `iphone_backup`, every `check_interval`) records an `IPhoneBackupReport`; each backup folder has a row in `iphone_backups` (migration 0004: state, baseline and pending sizes, last full read), keyed by folder because two folders can carry the same UDID. A state change appends `iphone_backup_changed` (subject = folder; recorded only on change, like drive health). Each configured folder is checked on its own: one that cannot be read is reported and alerted without hiding the others. Problems and "no backup on this computer" alert every `notify.repeat_every` per folder and condition; alerts never name the device or its identifiers.
- **Copies (`internal/iphonecopy`, `iphone_backup.keep`, default 3):** each healthy (ok) backup is copied into `<storage.root>/iPhone backups/<UDID>/<stamp>/`, where `<stamp>` is when it finished (UTC): the folder exactly as Apple's tool wrote it (restore by copying it back into `MobileSync\Backup\<UDID>`), plus `<stamp>.sha256` in `sha256sum`'s format (verifiable with `sha256sum -c`). A copy is complete once its manifest exists; it is built in `.partial-<stamp>/`, its manifest written beside it, then the folder and the manifest renamed into place (`Recover` completes or discards an interrupted copy). The source is hashed first, then each file whose SHA-256 matches the base copy's (the newest copy with no damaged files) is a **hard link** to it and every other is copied and must hash to the manifest's value while it is read; the copy is kept only if the source still holds the same finished backup afterwards (otherwise the next check copies it). So every further copy costs only what changed, and removing an old copy leaves the files newer ones share. Every operation goes through an `os.Root` on the copies folder, and a file is always written under a new name (whatever stands at the name is removed first, never written through: incoming is shared with another computer); manifest paths are limited to the names Apple's tools write (`[A-Za-z0-9._-]` components, at most 4 deep), so a manifest can never name a path outside its copy. A first copy must leave `storage.min_free_percent` free. Copies beyond `keep` are removed oldest first, manifest first. Copies are re-hashed every `read_interval`, all of a device's copies in one pass so a file they share is read once (`platform.FileID`: device and inode, or volume serial and file index); this runs before any new copy, so a damaged copy is never a base. Damage is alerted (urgent) and kept on record; a file damaged on disk is shared by every copy linked to it until that check finds it, after which the next copy is written whole. Ledger: migration 0006 `iphone_backup_copies` (one row per copy: size, bytes written, last verification, damaged files), reconciled with the disk at every check; events `iphone_backup_copied`, `iphone_backup_copy_removed` (`retention` / `missing`), `iphone_backup_copy_damaged`, `iphone_backup_push_refused`.
- **Pushed from another computer (NAS mode, owner decision 2026-10-07):** the NAS cannot read the PC's backups itself: UGOS Pro's interface cannot mount another computer's share, and a Docker CIFS volume stops the container from starting while the PC is off. So the PC pushes: `homecloud iphone push --from <Apple's folder> --to <share>` (scheduled with `install-push`: a Task Scheduler logon task repeating every `--every`, or a systemd user timer) hashes each finished backup, reads `archived-<stamp>.sha256` (the manifest of the copy the archive will build on, which the archive publishes) and sends only the files whose SHA-256 differs, into `<incoming>/<UDID>/.push-<stamp>/`, then its full manifest and `<stamp>.sig`; renaming the folder and then the manifest into place commits the push (a folder renamed without its manifest was never committed and is cleared by the next push). An interrupted push resumes (files already there with the right hash are not sent again). **Push key (2026-10-07 audit):** incoming is a shared folder, so anything that can write to it could push a backup of its making, and a backup dated in the future would outlive every genuine copy in pruning. Each push is therefore signed: HMAC-SHA256 with a 256-bit key over the device, the stamp and the manifest (which names every file with its SHA-256). The key is created where the archive is (`homecloud iphone push-key`) and saved on the computer that pushes (`push-key --set`), owner-only in each one's state directory (`iphone-push.key`), never in the archive or incoming. Without it the archive leaves pushes waiting and alerts; doctor reports a missing key as a setup step, not a failure, since in a container it is created with the agent running. The archive's check (`iphone_backup.incoming`) takes each committed, correctly signed push in oldest first, linking unchanged files from its base copy and checking every received file against the manifest (regular files only); before the copy is kept, its own plists must pass what this computer's backups must pass to be copied (`iphonebackup.Judge`, age aside), name the device it is filed under exactly, and give the time it is filed under. A push that does not match (or names a file the base lacks) is refused, recorded and alerted, and removed, so the next push sends it again; a push the archive volume has no room for, or that arrives below `storage.min_free_percent`, waits. Manifests are capped (2^21 files, 256 MiB). Devices known only from copies are judged by their newest copy (damaged files count as unreadable, its last verification as the last full read). Uses Windows' own SMB client and credential store; the NAS never holds a PC password.
- **Owner steps** (where Apple's USB connection works; otherwise homecloud#15, backups made on Linux): install Apple Devices, connect the iPhone, tick "Encrypt local backup", back up once; then keep it connected or on the same Wi-Fi regularly. Until the first backup the app shows "No iPhone backup on this computer yet".

## 8f. iCloud sign-in for iCloud Drive (implemented, P2 milestone B1)

- **Why our own client:** rclone's `iclouddrive` backend deletes valid Pages/Numbers/Keynote downloads (package ZIP smaller than the listed size; rclone #8404, #9798), exposes no hashes and cannot express "archive, never delete"; kei's session is private to kei (and two clients would race rotating the same tokens). `internal/icloud` signs in as iCloud.com does; `internal/drive` reads Drive.
- **Sign-in (`homecloud icloud login`, owner only, in a terminal):** SRP-6a (`/signin/init`, `/signin/complete`; RFC 5054 2048-bit group, SHA-256, PBKDF2 `s2k`/`s2k_fo`, Apple's conventions: no account name in x, lowercase account name in M1, A and S padded, B as received) → on 409 a code: `PUT /verify/trusteddevice/securitycode` pushes it (no longer automatic since iOS 26.4), or `sms N` texts a trusted number read from `GET /appleauth/auth` (JSON or the page's `boot_args`); a valid code may be answered 409 with `securityCode.valid` or a new `X-Apple-Session-Token` → **escrow** when a 409 carries `X-Apple-EDP`/`X-Apple-PDP`: a second SRP proof with an empty account name (`/escrow/init`, `/escrow/complete` with K) → `GET /2sv/trust` (trust token) → `setup/ws/1/accountLogin` (web cookies + service map) → under Advanced Data Protection, `requestPCS` for `iclouddrive`, approved on a trusted device. A later sign-in that presents the trust token needs only the password (and escrow), no code.
- **Sources:** request sequence and headers as icloud-photos-sync PR #1124 (merged 2026-10-05, live-tested incl. escrow; GPL-3.0, used as protocol reference only); SRP adapted from rclone (MIT, see `THIRD_PARTY_NOTICES.md`) and checked against icloud-photos-sync's reference vectors (two real iCloud exchanges, `s2k_fo`, leading-zero padding of A, B and S — all match). Client id = iCloud.com's public web client id (same in both).
- **Session:** `icloud-session.json` in the per-user state dir, written owner-only and atomically (`platform.WriteSecretFile`): cookies as received (replayed into a standard `cookiejar` with the public suffix list; Max-Age stored as absolute expiry), session token, trust token, account country, service map, signed-in time. **The password is never stored.**
- **Unattended use:** a call answered 401/421 refreshes once (`setup/ws/1/validate` with the cookies, then `accountLogin` with the session and trust tokens). When Apple refuses, or asks for a code again (`hsaChallengeRequired`), or Drive needs ADP approval again (423), the result is `ErrSignInRequired` and the owner runs `homecloud icloud login` again (a Drive run outcome, an app state and an alert every `notify.repeat_every`).
- **Sign-in hygiene:** each `homecloud icloud login` starts a fresh session, keeping only the trust token, and only for the same Apple ID; the password is held as bytes and cleared when the sign-in ends; wrong password (401) and refused account (403) are told apart; JSON calls never follow redirects, so tokens reach only Apple's endpoints; every call is bounded by `icloud.request_timeout` and a response by 32 MiB. The agent and the CLI save the session under a shared file lock, and the agent saves only when the file is unchanged since it read it.
- **Drive listing (`homecloud drive ls`, B1 spike):** `retrieveItemDetailsInFolders` on drivews (root `FOLDER::com.apple.CloudDocs::root`); item types FOLDER, FILE, APP_LIBRARY, APP_CONTAINER; an unknown type is an error, never skipped.

## 8g. iCloud Drive archive (implemented, P2 milestone B2)

- **Layout:** `<storage.root>/Drive/iCloud Drive/…` mirrors the Files app's iCloud Drive; `Drive/App Libraries/<Name> (<zone>)/…` holds each app's iCloud folder (`retrieveAppLibraries`; names repeat across apps, so the zone is part of the folder name). `Drive/.versions/<UTC time>/<path>` keeps every copy a newer one replaced; `Drive/manifest.csv` lists every archived file (including those deleted in iCloud); `Drive/.partial` holds downloads in progress and is the only place homecloud deletes from. Every file operation of a sync goes through an `os.Root` on `Drive/`, which refuses names, links and junctions leading outside it; scrub reads only paths inside it.
- **Sync (run kind `drive_sync`, every `drive.sync_interval`, after the cycle):** preflight as the cycle (archive present, free space) → a full walk in **scopes**: the iCloud Drive tree (must list completely, or the run fails) and each app's folder, listed on its own (folders in batches of 10). `retrieveAppLibraries` also returns apps that keep no documents in iCloud Drive (Messages, Notes, Mail, banking and chat apps: drivews answers 502 for them, consistently, on this account) and apps whose folder was never created (`"status":"ID_INVALID"`, treated as empty); an app folder that cannot be listed is counted (`unlisted_apps`), and is a failure only when it holds archived files. Deletions are recorded only within scopes listed completely, so a failed or partial listing can never look like deletions → per file, by drivewsid: new → download; etag changed or copy damaged → download (same bytes again: metadata only, no version); iCloud path changed → move the copy (empty folders left behind are removed); missing from a complete walk → `deleted_in_icloud_at` recorded, copy kept; seen again → restored. Nothing at a target path is ever overwritten: it moves to `.versions` first.
- **Verification at download:** plain files must match their listed size and **Apple's content signature** from the download token: `0x01 || SHA-1("com.apple.XattrObjectSalt\0com.apple.DataObjectSalt\0" || bytes)`, confirmed against real downloads of this account (2026-10-06) — an end-to-end check against iCloud's own record. Packages (iWork and other bundles) download as a ZIP whose size never matches the listing; every entry is read so the ZIP reader checks its CRC-32. Empty files are created without a download (iCloud refuses to serve them). homecloud records its own SHA-256 of every copy.
- **Scrub:** the weekly scrub re-hashes the same share (`schedule.scrub_fraction`) of Drive files; a copy that no longer matches is marked damaged and alerted, and the next sync downloads it again, keeping the damaged copy under `.versions`.
- **Names:** each iCloud name is made safe on Windows (`<>:"/\|?*` and control characters → `_`, trailing dots/spaces kept as `_`, device names such as `CON` prefixed with `_`, over-long names shortened with a hash); two items whose local paths clash (differ only in case, or a file where another item needs a folder) are told apart by ` (<first 8 of the document id>)` before the extension, then the whole id: a folder takes its own id, so all its files stay together. The ledger keeps each file's local path, so names never shift later.
- **Crash safety:** a move is recorded in the ledger as soon as the copy moved, before any download; each move re-runs safely after a crash (a copy already at its target is recognised, a case-only rename goes through the same file). Downloads land in `.partial/<SHA-256 of the drivewsid>` and are renamed into place only after their checks; one that receives nothing for `drive.stall_timeout` is abandoned and retried at the next sync. A sign-in failure during downloads ends the run as `sign_in_required`. `manifest.csv` is rewritten after every sync, also a failed or interrupted one. The ledger runs SQLite in WAL mode with `synchronous=FULL`: sqlite.org documents that WAL with `NORMAL` can lose committed transactions on power loss.
- **Session:** the agent loads homecloud's iCloud session at each sync and saves renewed cookies afterwards only if the file is unchanged since it read it, so a `homecloud icloud login` during a sync always wins. An expired session ends the run with `sign_in_required` and alerts every `notify.repeat_every`.
- **Ledger:** migration 0003, table `icloud_drive_files` (never deleted rows); events `drive_file_archived`, `drive_file_changed` (with `kept_as`), `drive_file_moved`, `drive_file_deleted`, `drive_file_restored`, `drive_file_damaged`, `drive_file_repaired` (a damaged copy downloaded again; library `icloud_drive`, asset id = drivewsid).
- **Advanced Data Protection:** this account uses it; Drive needs the `X-APPLE-WEBAUTH-PCS-Documents` cookie approved at sign-in, a session cookie without expiry. Its real lifetime is observed from the `drive_sync` outcomes.

## 8i. Remote access (NAS mode, milestone 3)

- **Design:** the agent keeps listening on loopback only. On the NAS a Tailscale container shares the agent's network namespace and serves it with Tailscale Serve (`deploy/compose.yaml`, `deploy/serve.json`; image `tailscale/tailscale:v1.102.5` pinned by digest, userspace networking): tailnet only, HTTPS with a Let's Encrypt certificate for `<host>.<tailnet>.ts.net`, nothing published on the LAN or the internet. Tailscale's guidance is to keep a served service on localhost (docs "Tailscale Serve").
- **Tailnet grant:** in userspace networking, tailscaled forwards a tailnet TCP connection to any port of the node to `127.0.0.1` at that port (`wgengine/netstack/netstack.go`, `acceptTCP`, at v1.102.5), so tailnet devices also reach the agent's plain-HTTP listener, where requests still need credentials and the agent cannot tell them from local ones. So the node joins as `tag:homecloud` (`TS_EXTRA_ARGS=--advertise-tags=tag:homecloud`; a tagged node loses its user identity and is matched only by its tag, never by `autogroup:member`, Tailscale kb 1068) and the policy grants `autogroup:member` → `tag:homecloud` `tcp:443` alone, with `tagOwners` letting `autogroup:admin` apply the tag (without it `tailscale up` refuses the tag) and the default allow-all narrowed to `"dst": ["autogroup:member"]` so nothing else reaches the node (README). The tag also gives the node no way into the tailnet: no grant has it as a source. The policy's `tests` assert that a member reaches `tag:homecloud:443` and not the agent's port; Tailscale runs them on every policy change and rejects a change that fails one (kb 1337).
- **What the agent sees:** for a proxy target, Serve forwards the request with the client's Host (`r.Out.Host = r.In.Host`, `ipn/ipnlocal/serve.go` at v1.102.3), plus `X-Forwarded-Host/Proto`. So `web.public_origin` (required: `""` or a lowercase https origin) adds exactly that host to the Host check and that origin to the Origin and CSRF lists; every other check is unchanged. With a public origin, session cookies are `Secure`.
- **Signing in:** one model for every client: one-time login codes, minted only with the bearer token on the agent's host, each for one purpose. `homecloud open --print` prints the sign-in link at the public origin (on the NAS: `docker compose exec homecloud homecloud open --print`), `homecloud pair` a pairing code. Tailscale's identity headers are not used as credentials.
- **Verified live (2026-10-06, image `3ebdf43` + `tailscale/tailscale:v1.102.5`, ephemeral auth key):** the app loads at `https://<host>.<tailnet>.ts.net` with a valid certificate and as a secure context; the API refuses calls without credentials; a foreign Host is refused; `homecloud open --print` inside the container signs a browser in; the desktop app pairs through its Settings form (token stored as a generic Windows credential), is told to pair again after a revocation from the browser, and **Disconnect** revokes it there and deletes the credential. Neither container publishes a port. Two findings fixed in `deploy/`: `TZ` for local times in the CLI, and Tailscale appending `-1` to a taken name (so `web.public_origin` must match the name `tailscale status` shows). A container without an auth key gives up after about a minute and restarts with a new login link, so the first start needs `TS_AUTHKEY`.
- **Alternatives rejected:** listening on the LAN (needs a private CA on every device, exposes the API to every LAN device, cleartext without it); Cloudflare Tunnel (puts the app on the internet, the proxy sees the traffic); plain WireGuard (an open port and a public IP, fails behind CGNAT); Headscale (a server to run). Tailscale's free Personal plan: up to 6 users, unlimited user devices (tailscale.com/pricing, 2026-10-06).

## 8j. Paired devices (NAS mode, milestone 4)

- **Credential:** a device token, 256 random bits, returned once by `PairDevice` in exchange for a one-time pairing code (`homecloud pair`; minted like a sign-in code, but refused for signing in and the reverse). Every pairing sends an alert (naming no device): a device keeps its access until it is revoked. The agent stores only its SHA-256 (migration 0005, `paired_devices`; rows are never deleted, revocation sets `revoked_at`) and looks it up per request, so a revocation takes effect at once, open streams and media links included (`auth.Valid`). Revoking a device that may be in someone else's hands also calls for a new `notify.topic`: it has seen the topic alerts go to. Last-seen is written at most once a minute per device.
- **Rights:** a device token can do what a browser session can (`KindDevice`), not mint login codes, which stays with the agent token on the agent's host. `PairDevice` is open like `ExchangeLoginCode` (the code is the credential) but sets no cookie, so it needs no CSRF check; the Origin allow-list still applies. A device store that cannot be read answers `Unavailable`, never admits.
- **Desktop app:** two modes, kept in `connection.json` in the app's config directory: this PC's agent (discovery file and its rotating token, as before) or a paired homecloud (`https://<host>.ts.net`, validated in Rust; the CSP allows `https://*.ts.net` and nothing else remote). The token is kept in the OS credential store through `keyring-core` with one store crate per platform (Windows Credential Manager with Local persistence, so it never roams; the Secret Service on Linux), under service `homecloud` and the address; the store is opened on first use and every command runs off the main thread. The mode is read before the first render, so this-PC-only actions (start the agent, show a file in its folder) are not offered for a NAS. A rejected device token is not retried: the app asks to pair again. **Disconnect** revokes the device there first; **Forget anyway** covers an unreachable homecloud (revoke it there under Paired devices).

## 8k. Security and access (2026-10-07 audit)

- **Archive access:** the archive is the only copy of the library, Hidden photos included, so `storage.root`, `backup.dir` and kei's folder (its config and its sync report name the Apple Account) are the agent's user's alone: `platform.MakePrivate` sets a protected DACL `D:P(A;OICI;FA;;;<user SID>)(A;OICI;FA;;;SY)(A;OICI;FA;;;BA)` on Windows (the entries of a user profile; `SetNamedSecurityInfo` propagates them to everything already inside, replacing what it inherited, per its documentation) and mode 0700 on Linux (a folder owned by another account is an error: its owner must hand it over). The agent applies it to `storage.root` at every start (a no-op once done) and `archive init` when it marks an archive; kei's folder and `backup.dir` when they are written. Found 2026-10-07: `E:\HomeCloud` inherited `Authenticated Users: Modify` and `Users: Read` from the drive's root, as every data drive does by default, so any other account or low-privilege service could read or change the ledger and the library. `homecloud doctor` reports any account but the owner, SYSTEM and Administrators (`platform.CheckPrivate`).
- **Paths from outside:** kei's `local_path` must be absolute and inside kei's download folder (`kei.DownloadDir`) or the manifest is refused, since homecloud reads, renders and serves that file; Drive paths are confined as in §8g; `iphone_backup.incoming` must be apart from the archive, `backup.dir` and Apple's folders (the agent removes what it takes in from there and writes receipts beside it).
- **Pushed iPhone backups:** signed with a push key and checked against their own plists before they are kept (§8e). A new copy counts as verified when the copy it shares files with was, not when it was made.
- **Errors and alerts:** errors never carry a request URL (net/http's `*url.Error` prints it with its query, and Apple's URLs carry tokens: `icloud.withoutURL`); downloads are named by host. ntfy messages count, never name: no file, device, drive model, serial number or path.

- **Desktop app:** the page may call only the app's own commands and the log plugin's `log` command (no `core:*` permission: the page uses no core API); `Object.prototype` is frozen before the page runs (`freezePrototype`; the UI tests run frozen too); a remote address is read with the WHATWG URL parser (`url` crate, as the webview reads it) and must come back unchanged, so `https://evil.com\.ts.net` (host `evil.com`) and anything with a user, port, path or capitals are refused; `schtasks.exe` is started from the system directory (`GetSystemDirectoryW`), not looked up next to the app first as Rust's `Command` does; "show in folder" accepts only drive-letter paths on Windows, so a UNC path never makes Explorer, or even the existence check, contact another computer.
- **Copied commands:** PowerShell also ends a single-quoted string at the typographic quotes U+2018–U+201B (checked in PowerShell 7.6 and 5.1), so the web app doubles those as well as `'`.
- **Supply chain:** CI actions are pinned to commit SHAs (the version in a comment) and checked out without persisted credentials; runners are named by OS version, never `-latest` (`ubuntu-24.04`, `windows-2025`), so an image change is a deliberate commit: Linux jobs run on the oldest supported release (glibc 2.39), because a Linux build, the Tauri `.deb` above all, needs at least the glibc it was built against (Tauri's distribution guide), and the tests then cover the oldest supported kernel and tools; Dependabot proposes monthly, grouped updates of the actions, Go modules, Cargo crates, base images (not pnpm's, which moves with `packageManager`) and the compose image, none for a release under 7 days old where the registry gives publication dates (ghcr.io does not: its first image update came the day after the release); the web app's packages, which Dependabot cannot update (pnpm 12), are checked by `pnpm audit` in CI; Vite is 8.3.3 (three dev-server advisories of 2026-10-06).

## 8l. Logging (2026-10-07 review)

Reviewed against two days of the live logs: 97% of `kei.log` was kei's info line for every asset already on disk, with colour codes; 42 agent starts had no matching stop, so a crash looked like a restart; four DNG files that ffmpeg cannot decode were logged with ffmpeg's full output on every pass; a partial kei sync did not say which assets failed; iCloud Drive item failures and run durations were not logged at all.

- **One shape:** every agent line is JSON (`log/slog`) with a constant lowercase message saying what happened and what happens next, snake_case keys, and the context it was logged in; `sloglint` (golangci-lint) enforces it. Nothing secret is logged: no token, cookie, code, ntfy topic or Apple ID; Apple's signed URLs are cut to their host (`icloud.withoutURL`, `kei.withoutURLs`); a principal is logged as its kind and id or handle (`auth.Principal.LogValue`), never a credential.
- **Runs:** `recordRun` records every run (cycle and maintenance jobs) and logs `run started` and `run finished` (`ok`, `duration_ms`, `err`; error level on an error, warning when not ok). Lines logged during a run carry its `run` id and `run_kind` (`internal/logging`), matching the ledger's `runs` row the app shows.
- **kei:** runs with `--log-level warn` and `NO_COLOR=1` (tracing-subscriber 0.3.23, which kei 0.26.0 uses, writes colour codes unless `NO_COLOR` is set), so `kei.log` holds kei's warnings and errors only. What the sync did comes from kei's JSON report (`kei.ReadReport`: schema 3, only a report written after the sync started, never its options, which name the account) as one `kei sync finished` line: outcome, counts, duration, listing problems and the failed assets with kei's error (signed URLs cut to their host); warning level when anything needs a look.
- **Failures once:** a rendering that fails is logged once until it succeeds (`thumbs.Renderer`), however often the preview pass or the library asks for it; an iCloud Drive item that is not archived is logged each sync with its path, and the sync's summary is a warning then.
- **Owner actions and faults:** sign-ins, refused codes, pairings, revocations, sign-outs, issued codes, sync requests, test alerts, quarantine releases (with the reason) and repair requests are logged with who made them; every alert sent or not sent is logged with its title. API answers that are the agent's own fault (internal, unknown, data loss, unavailable) are logged by a Connect server interceptor (`web.faults`) with the cause the caller never receives (`connect.Error.WithCause`); a caller's refusals are not.
- **Process:** the start line has the version, process id and config path; the end is one line, `homecloud-agent not started` or `homecloud-agent stopped`, with the error. Windows ends the agent without notice (logoff, shutdown, `schtasks /End`), which writes no line: the next start logs the runs it left unfinished. A crash (an unhandled panic or fatal error) goes to `homecloud-agent-crash.log` (`debug.SetCrashOutput`; a windowsgui process has no stderr); the next start logs its first line as the cause and keeps it as `homecloud-agent-crash-<UTC time>.log` (newest `logs.max_backups` kept). On Linux the crash goes to stderr.
- **Scheduled iPhone push (Windows):** a console program started by Task Scheduler gets a console window, so an hourly push flashed one (measured 2026-10-07: a probe started by a logon task got a console). The CLI's embedded manifest (`cmd/homecloud/homecloud.exe.manifest`, compiled by `go generate` with goversioninfo into `rsrc_windows_*.syso`, which CI regenerates and compares) sets `consoleAllocationPolicy` to `detached` (Windows 11 24H2+, ignored before): started from a terminal it uses that terminal as before; started by Task Scheduler it gets no console and no standard output at all (measured: console window and stdout handle both 0). So `install-push` registers the push with `--log` wherever a task's output is not kept (`platform.TaskOutputKept`; systemd keeps it in the journal): `iphone-push.log` in the log folder, JSON lines from `push started` to `push finished` (`ok`, `duration_ms`, `err`), one line per device's backup (pushed, already archived, waiting to be taken in, still running, changed while sent) and per failure; 1 MiB files, 3 kept. The task still exits non-zero when the push failed, which Task Scheduler shows as its last result. Verified end to end with a temporary logon task: the log recorded the push and its failure, last result 1.
- **Where:** Windows logs live in `%LOCALAPPDATA%\homecloud\logs`, off the archive drive, so a missing drive is logged too (they were under `storage.root\logs`). Under systemd each line starts with its syslog priority (`<3>`, `<4>`, `<6>`; sd-daemon(3)) when `$JOURNAL_STREAM` names stderr's device and inode (systemd.exec(5)), so `journalctl -p warning` finds the problems; kei's lines are warnings, or errors when kei says so.
- **Desktop app:** tauri-plugin-log writes to the app's log directory (`%LOCALAPPDATA%\<identifier>\logs`, `~/.local/share/<identifier>/logs`): the app's own lines and the page's at info, libraries at warning (their debug output was asset lookups and credential store calls), 1 MiB files with 5 kept (the plugin's default kept one 40 KB file). Its commands log their failures, pairing and switching back to this PC's agent are logged, and the page's crashes and unhandled errors are written there (React's root `onCaughtError`/`onUncaughtError`, window `error`/`unhandledrejection`) while an error boundary shows a reload screen instead of a blank window. The page may call only the plugin's `log` command (`log:allow-log`).

## 8m. Files: phone uploads and a file manager (#23, planned 2026-10-31)

The owner wants Google Drive's **Upload** on the phone, saving into a folder of their choosing on this PC's drive or on the NAS, plus browsing, downloading, renaming, moving and deleting there. It is part of the agent and its web app, so it uses the same sign-in, the same Tailscale address and the same paired devices, and it moves to the NAS with the agent.

- **Locations, not the whole disk:** `[[files.locations]]` names each folder the app may touch (`name`, an absolute `path`; names unique ignoring case). A location must be apart from `storage.root`, `backup.dir` and the iPhone backup folders (neither the same folder nor inside the other, `config.nested`), and from every other location, so the archive kei and the ledger own is never written by hand. With no location the Files page says how to add one.
- **Confinement:** every operation opens its location as an `os.Root` (Go 1.24+; rename, link and the rest since 1.25), so `..` and symbolic links cannot leave it. Paths in the API are slash-separated and relative to the location; a component may not be empty, `.` or `..`, nor contain `\`, NUL or a character Windows refuses (`<>:"|?*`, control characters), nor end in a dot or space, so a name valid on the NAS is valid on Windows too. Each location keeps homecloud's own data in `.homecloud/` at its top (uploads in progress, the trash), which listings hide and paths may not name.
- **No overwrite, ever:** an upload, rename, move or restore never replaces an existing name. Uploads and restores that meet one take the next free `name (2).ext`, as Drive does; a rename or move refuses with `AlreadyExists`. The agent runs every change in a location under one lock, so its own operations cannot race; a program on the computer itself could still create a name between the check and the rename (Windows' rename replaces a file, and `os.Root` exposes no no-replace rename).
- **Deleting goes to the trash:** a deleted file or folder moves to `.homecloud/trash/<id>/` with a small JSON record (its original path and when it was deleted), and the Trash view restores it to its original folder (recreated if it is gone). Items older than `files.trash_retention` (1–90 days) are purged hourly. Nothing is removed outright from the phone.
- **Uploads are resumable (tus 1.0):** `tusd` v2 (`pkg/handler` with `pkg/filestore` and `pkg/memorylocker`: one agent process owns every upload) behind `/files/uploads/<location>/`, and `tus-js-client` v4 in the app. An upload is written into its location's `.homecloud/uploads/`, on the same volume as its destination, so finishing it is a rename, not a copy. Creation (`PreUploadCreateCallback`) needs a known length that fits the volume's free space and a valid name and existing destination folder in its metadata; completion (`PreFinishResponseCallback`) moves it into place and answers with the name it was saved as. A connection that drops resumes from the last byte the agent wrote; an unfinished upload is removed after `files.upload_expiry` (1–30 days). tusd extends the read deadline per read (`NetworkTimeout`), so the server's 30-second read timeout bounds idle connections, not long uploads. tusd's own CORS handling and its GET and concatenation routes are off: the agent's CORS policy covers the tus methods and headers, and downloads are the agent's own route.
- **Downloads:** `GetFileLink` returns a signed, principal-bound link (the `/media` signer and its validity, so a long video keeps streaming) to `GET /files/download/<location>/<path>`, served with `http.ServeContent` (ranges, so videos stream) and `Content-Disposition: attachment` unless the page asks to view it. Like media links, a link stops working when its sign-in or device is revoked.
- **Access:** the upload routes accept the same credentials as the API and apply the same rules (a browser session must pass the CSRF check; a device token may upload). Every change is logged with its principal, location and action, never a file name (§8l); there are no alerts.
- **iPhone uploads:** Safari's file picker hands photos from the Photos library over as JPEG and may re-encode videos (reported on Apple's developer forums; to be measured on the owner's iPhone before the page says so). Files chosen through **Browse** (the Files app) arrive unchanged; the Files page says which to use for originals.
- **Rejected:** Nextcloud, Seafile, File Browser and similar servers (another stack, another sign-in and another Tailscale service to run for one feature); SMB through the iPhone Files app (no resume, needs the share opened to the tailnet on every computer, and offers nothing on the NAS the agent does not); uploads through the Connect API (requests are capped at 1 MiB and are not resumable).

## 10. Spike findings

### kei configuration semantics (verified against kei v0.24.1 docs and source; re-checked for v0.25.0, v0.25.3 and v0.26.0, whose config, report, manifest and exit codes are unchanged; 0.26.0 migrates kei's state to schema 36, which older kei cannot open)

- **One copy per asset:** `[filters] albums = ["none"]`, `unfiled = true`. The unfiled pass excludes only members of *selected* albums (`compute_unfiled_exclude_ids` in `src/commands/service.rs` returns an empty set when no album is selected), so it enumerates the whole library. Album passes would write one extra copy per album membership (wiki *Folder Structure*).
- **Completeness for deletion:** `photos.edited = true` and `photos.alternative = true` so edits and RAW siblings are archived before an asset can ever be deleted; `live_photo_mode = "both"`.
- **Filenames:** `keep_unicode_in_filenames = true` (lossless names); `file_match_policy = "name-id7"` (asset-ID-qualified names, no size-based collision heuristics).
- **State location:** kei documents `data_dir` as defaulting to the config file's parent, but on this machine `kei status` reports its state DB and session under `%USERPROFILE%\.config\kei\cookies\` (observed 2026-10-05; the config lives at `<root>\kei\config.toml`). From kei 0.25.0 the state, session, cache and lock files there are named by a hash of the exact Apple Account name and realm, and every state command checks the database's account owner; a database from 0.24.1 is adopted once with `kei migrate-state --legacy-db <db> --confirm-ownership`, which needs a fresh password login (docs/account-state-migration.md). kei's state is therefore on the system drive, not with the archive; losing it costs a re-enumeration, not files. Not changed: pointing `data_dir` elsewhere would start kei with an empty state.
- **Hidden photos are not in the library-wide pass (found 2026-10-05):** with `albums = ["none"]` + `unfiled = true`, kei's only pass is `library.all()` (iCloud's "All Photos"), which excludes Hidden items. An interrupted album/metadata refresh run downloaded 9 Hidden photos that had never been archived. With `icloud.include_hidden = true` the generated config adds the Hidden smart-folder pass (a named smart folder needs no `all-with-sensitive`), written under `Photos/Hidden/%Y/%m` and hidden on disk after each cycle (`platform.MarkHidden`: the Windows hidden attribute; on Linux an entry in `Photos/.hidden`, honoured by Nautilus, the GTK file chooser, Dolphin and Konqueror, not Thunar). It cannot be a dot-folder: kei strips leading dots from every path component (`sanitize_path_component`), which the first run showed (`PhotosHidden`).
- **homecloud generates kei's config** (`kei.RenderConfig`, written by the agent at startup with an owner-only DACL/0600 because it names the Apple Account; `homecloud doctor` reports drift). Every archive-relevant kei option is fixed in code rather than hand-edited: originals of every rendition, one `%Y/%m` tree for unfiled *and* album passes (`folder_structure_albums = "%Y/%m"`, so no pass can create album-folder duplicates), XMP sidecars, the Hidden pass. Verified by `kei config show` with kei 0.24.1.
- **Sidecars:** `[metadata] xmp_sidecar = true` writes XMP next to newly downloaded files, for other tools that read the archive; homecloud does not read them (#17 takes the metadata from kei's manifest). Every normal sync also rewrites existing sidecars in bounded batches ("Applying metadata rewrites to on-disk files count=500" in kei's log), but that does not create missing ones: on 2026-10-24, 1,170 of 3,899 originals had no sidecar, every one from 2022–2023, while kei's catalog held their metadata (a location for 1,373 of those years' 1,569 assets). kei documents no automatic sweep of stale sidecars (docs/metadata.md, rhoopr/kei#799) and nothing about missing ones. `kei sync --refresh-metadata` requires a config without `albums`/`smart_folders` keys, which makes kei run album passes; with the old `{album}` template that downloaded album copies and re-pointed 67 assets to them (homecloud re-verified them at the new paths; the identical date-folder twins were moved to `_tidy/`). Changing the path settings makes kei reconcile recorded paths ("Download path config changed since last sync; … staging local reconciliation").
- **Download integrity (kei-side):** bytes received must equal both `Content-Length` and the API `size`, otherwise retry (wiki *Download Pipeline*); SHA-256 recorded at download time (`verify --checksums`). Apple's `fileChecksum` is an MMCS signature, not a content hash.
- **Auth:** SRP + trusted-device 2FA; credentials via Windows Credential Manager (`kei password set`); headless runs exit **3** when 2FA is needed; `kei login get-code` / `submit-code` for non-interactive completion.
- **Checkpoint (sync token):** after a sync kei saves its place in each iCloud zone, so the next sync lists only the changes since then. When it cannot prove a sync saw everything it keeps the previous place instead, and its report says so (`stats.sync_token_blocked`, with `_reason` from a vocabulary kei extends, `_source` `kei`/`icloud`/`unknown`, `_explanation`, `_zone`; `full_enumeration_reason` when the sync listed the whole library; kei `SyncStats`, `src/download/orchestration/models.rs`, v0.26.0). Keeping it for one sync is by design (e.g. the one full listing after kei's settings or its enumeration hash change), and nothing is downloaded twice; keeping it sync after sync means each sync lists the whole library again (~6 min instead of ~20 s for 3,899 assets) and kei is stuck. **Found 2026-10-09:** after the 0.25.0 upgrade kei's delta bridge from the pre-upgrade place failed every cycle for 13 hours (`inventory_delta_bridge_failed`, rhoopr/kei#924) while every cycle ended OK. homecloud records kei's words on each cycle (`CycleReport.checkpoint`, with the syncs in a row that kept it; a cycle without a kei report neither counts nor resets the count), the overview shows the latest, and `kei.checkpoint_alert_cycles` syncs in a row (2–100; one is normal) alert through `alertRepeated` and the app's banner. kei keeps no such count itself (`health.json` counts failures; `kei status` is text only). **Indexing:** up to 0.25.1 kei stopped with the generic exit code 1 whenever Apple's `CheckIndexingState` answered `RUNNING` (6 of 25 cycles on 2026-10-08/09 were reported as failed downloads). From 0.25.2 it downloads during `RUNNING`, keeps its checkpoint, and moves it only after a complete listing once Apple reports `FINISHED` (kei CHANGELOG 0.25.2/0.25.3, rhoopr/kei#926). A cycle that keeps the checkpoint counts toward the alert above, so indexing that never finishes is not silent. A missing or unknown indexing answer still fails with exit code 1, which is a real failure. **Recovery** when the checkpoint stays kept: first check that kei is not holding it for indexing or recovery (its warning in `kei.log`), because kei's upgrade guide forbids resetting the checkpoint to hide that hold (docs/v0.25.3-upgrade.md, repeated in docs/v0.26.0-upgrade.md). Otherwise stop the agent, run `kei reset sync-token --yes --config <kei config>` (clears kei's places in iCloud, keeps its download history, so nothing is downloaded again), start the agent; the next sync lists the library once and saves a new place (2026-10-09: 335 s, then 17 s syncs).

### Spike B results (2026-10-05, real account, 300 most recent assets)

- `kei list libraries` → one library, `PrimarySync` (primary). No shared library.
- **Manifest grain:** one row per `(asset_id, version)`. Observed versions: `original`, `adjusted` (edits, photo and video). Rows carry `download_checksum` = `local_checksum` (lowercase hex SHA-256), exact `size_bytes`, RFC 3339 UTC `created_at` / `added_at` / `downloaded_at` / `last_seen_at`, `media_type` (`photo`/`video`), `status`, `albums`.
- **Independent verification:** 310/310 files re-hashed by homecloud tooling matched kei's SHA-256 and size.
- **Throughput:** 27.3 GiB in 7 m 48 s (~60 MB/s) — vs ~1 MB/s through iCloud for Windows.
- **Write-guard:** one download was rejected with "`.kei-tmp` changed identity" (kei refuses to publish a temp file whose identity changed mid-write; Defender real-time scanning is active on this host — cause unconfirmed) and succeeded on kei's per-asset retry. homecloud must therefore treat kei's per-run failure count as advisory and the manifest + its own hashing as the source of truth.
- **Live Photos** (kei `src/state/types.rs` + 1,814 live manifest rows): one `asset_id` carries the still as `version=original, media_type=live_photo_image` and the motion clip as `version=live_original, media_type=live_photo_video`; edited Live Photos add `adjusted` + `live_adjusted`. Version keys: `original, medium, thumb, adjusted, alternative, live_original, live_medium, live_thumb, live_adjusted`. Statuses: `pending, policy_excluded, downloaded, failed`. Unknown values are rejected (fail closed).
- **Ordering:** kei enumerates newest-first; pyicloud's `photos.all` yields oldest-first (first 400 = 2022-06..08). Identity comparison (Spike A) therefore runs after the full sync covers both ranges.

### Verification design corrections

- QuickTime `.mov` files may legitimately begin with `wide`, `mdat`, `moov`, `free`, `skip` or `pnot` rather than `ftyp` (wiki *Content Validation*). Tier 2 therefore validates a **contiguous top-level box chain ending exactly at EOF that contains `moov` and `mdat`**, and requires `ftyp` only for ISO-BMFF extensions (`.mp4`, `.m4v`; HEIC stills are photos and get no box walk).
- Tier 2 reads only top-level box headers (ISO/IEC 14496-12 §4.2: 32-bit size + type; size 1 ⇒ 64-bit largesize; size 0 ⇒ to EOF). That is ~60 lines of stdlib code, so the planned `abema/go-mp4` dependency was dropped.
- Tier 3 (`ffprobe -v error -show_entries format=duration:stream=codec_type,duration -of json`) requires exit 0, empty stderr, positive container duration and a video stream with positive duration. Live Photo clips carry extra `data` streams, which are ignored. Verified: a real iPhone MOV passes tiers 2–3; a copy truncated to 50 % fails both (ffprobe: "moov atom not found").
